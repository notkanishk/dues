# Queue the exceptions, capture the rest instantly

The existing prototype already has the right skeleton — one record type, one "next thing" per item, an attention list instead of a dashboard — and the research mostly confirms it; what the sources change is the detail. Expense products converge on a **two-level lifecycle** (a loose expense, then a batch whose status the expense inherits) and on attention queues that hold **only items needing human judgment**, each with a typed reason and an explicit "can't provide" escape hatch ([Zoho](https://www.zoho.com/us/expense/kb/expenses/expense-status/); [Navan](https://navan.com/blog/expense-exceptions-queue); [Spendesk](https://helpcenter.spendesk.com/en/articles/4153508-missing-receipts-send-reminders)). Statement reconciliation works best as a keyboard-driven review queue with a visible remaining-difference figure and a lock at the end, which the current spec lacks ([Actual](https://actualbudget.org/docs/accounts/reconciliation/); [Copilot](https://help.copilot.money/en/articles/7668990-bulk-editing-transactions)). The payment entry form should be a full-screen page rather than a bottom sheet, built on a plain text input with `inputmode="decimal"`, labels above fields, validation on blur and a save that only amount can block ([GOV.UK](https://design-system.service.gov.uk/components/text-input/); [NN/g](https://www.nngroup.com/articles/bottom-sheet/); [Baymard](https://baymard.com/blog/inline-form-validation)). Visually, the spec's palette passes text contrast in both themes by my own calculation, but its badges need a non-colour cue because the tints are indistinguishable from one another, and seven stages should be carried by about five hues plus shape ([Carbon](https://carbondesignsystem.com/patterns/status-indicator-pattern/); [WCAG 1.4.1](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)). The evidence is uneven: vendor help centres document states and flows but almost never colours, row layouts or font sizes, so every recommendation on density and "beauty" below is partly inference and is marked as such. The report ends with a prioritised change list for `mockup/DESIGN.md`, split into source-backed changes and inferences.

A note on reading this report: sentences carrying a link are cited findings. Passages introduced with "Inference:" are my synthesis from those findings and from the project context, and no source tested them directly. Contrast ratios and `Intl` outputs labelled "own calculation" were run locally in Node v26.13.0 against the hex values in `DESIGN.md`, not taken from a source.

## Expense apps converge on a two-level lifecycle with a "paid but unconfirmed" tail

### Loose items inherit the batch's status once claimed

Every expense product examined separates the pre-report life of an expense from the life of the report. Zoho gives a loose expense its own statuses — **Unreported** (on no report), **Unsubmitted** (on a draft report) — and once it sits on a report the expense simply takes the report's status ([Zoho expense status](https://www.zoho.com/us/expense/kb/expenses/expense-status/)). Report ladders are near-identical across vendors: Zoho runs Draft, Awaiting Approval, Recalled, Approved, Rejected, Reimbursed ([Zoho report status](https://www.zoho.com/us/expense/kb/reports/status-of-reports/)), and New Expensify runs Draft, Submitted/Outstanding, Approved, Paid, Done, where Draft stays editable and Done is locked ([Expensify](https://help.expensify.com/articles/new-expensify/reports-and-expenses/Understanding-Report-Statuses-and-Actions)). SAP Concur users describe the same shape as an "Available Expenses" pool from which items are picked into a report, with a "Personal Expense (do not reimburse)" marker — though that comes from a user forum and is configuration-dependent ([Concur community](https://community.concur.com/t5/Concur-Expense-Forum/Duplicate-Charge-showing-under-available-expenses-but-not-under/m-p/40267)).

The current spec already matches this: `Ready` is the available pool, `batch` is set once claimed, and batch status (Draft, Submitted, Reimbursed) drives the item to Claimed and Reimbursed. Two details from the sources are missing. First, Zoho has an explicit **Recalled** state for pulling a submitted report back to edit ([Zoho report status](https://www.zoho.com/us/expense/kb/reports/status-of-reports/)), and Expensify only allows duplicate resolution on Draft or Outstanding reports, requiring a retract first ([Expensify duplicate detection](https://help.expensify.com/articles/new-expensify/reports-and-expenses/Duplicate-Detection)). The spec offers `Discard draft` but nothing for a Submitted batch that turns out to contain a mistake. Second, Expensify splits **Paid** into sub-stages shown on hover: "Marked as paid" (paid outside the product), "Withdrawing", and "Confirmed" ([Expensify](https://help.expensify.com/articles/new-expensify/reports-and-expenses/Understanding-Report-Statuses-and-Actions)).

Inference: that last distinction maps exactly onto this user's situation. "Mark reimbursed" today is a single manual click, yet the spec already matches statement credits to refunds. A reimbursement credit landing in the Claimant's bank account is the same kind of evidence, so a batch should be able to sit at "Marked reimbursed" until a statement credit confirms it, at which point it becomes "Confirmed" and locks. Inference: a mapping onto Linear's fixed status categories is also useful for ordering and for the Board variant — Triage for unsorted statement lines and Amazon candidates, Todo for the three waiting stages, In Progress for Claimed, Done for Reimbursed, Canceled for Closed — because Linear keeps categories fixed and ordered while letting statuses vary inside them, and sends duplicates to Canceled rather than deleting them ([Linear workflows](https://linear.app/docs/configuring-workflows)).

### Queues hold only what needs judgment, typed by reason, with an exit

The attention pattern is consistent across vendors. Ramp puts a **"Missing items" section on the home page**, with each unmet field labelled in red "(required)" ([Ramp support](https://support.ramp.com/hc/en-us/articles/360042588454-Submitting-receipts-memos-and-accounting-for-your-Ramp-transactions)). Navan's exceptions queue gives each row a flagged transaction, a **suggested action, a rationale and a status**, and in-policy items never reach the queue at all ([Navan](https://navan.com/blog/expense-exceptions-queue)). Expensify collapses everything into one "Fix" badge on the review action ([Expensify](https://help.expensify.com/articles/new-expensify/reports-and-expenses/Understanding-Report-Statuses-and-Actions)). Pleo's accounting dashboard groups missing receipts and pending approvals under "needs attention" ([Pleo](https://blog.pleo.io/en/new-in-pleo-october)).

The spec's Needs attention section, with nine typed rules, one badge and one inline action each, is squarely in line with this. The gap is the exit. Ramp offers "I don't have a receipt" in the transaction menu ([Ramp support](https://support.ramp.com/hc/en-us/articles/360042588454-Submitting-receipts-memos-and-accounting-for-your-Ramp-transactions)), and Spendesk's "cannot be provided" **stops all future reminders** for that payment ([Spendesk](https://helpcenter.spendesk.com/en/articles/4153508-missing-receipts-send-reminders)). The spec handles the cab and QR-to-a-person case by attaching a payment-app screenshot as payment proof, which is a good equivalent, but an item with neither invoice nor screenshot will sit red forever. Linear adds a second exit: **snooze** (`H`) until a time or new activity ([Linear Triage](https://linear.app/docs/triage)). Inference: "Not delivered · 11 d" is the natural snooze candidate, since a late courier is nothing the user can act on; without snooze, red rows the user cannot clear will train him to ignore red.

Carbon supplies the ordering rule the spec already uses — when statuses are grouped, show the highest-attention colour — and a restraint rule it partly breaks: skip indicators entirely when no action is needed, because plain text is better ([Carbon](https://carbondesignsystem.com/patterns/status-indicator-pattern/)). The neutral badges `Handwritten bill`, `Payment not matched` and `Invoice on site` are informational; by Carbon's rule they belong as muted text on the row's second line, not as pills competing with real status.

### Receipts need a holding tray, and matching should key on the invoice

Receipt matching in card products keys on **amount, merchant and date within one calendar day**, and the documented failure modes read like this user's daily life: one receipt covering several charges, lookalike recurring charges, and Amazon order confirmations that do not match because the final amount changes ([Ramp matching](https://support.ramp.com/troubleshooting-transaction-receipt-matching)). Unmatched receipts get a visible home: Brex has "View unmatched receipts", from which a receipt can be assigned to an expense or used to create a reimbursement ([Brex](https://www.brex.com/product-announcements/manage-your-unmatched-receipts-in-one-place)).

paperless-ngx already provides that home. Its documented convention is an **inbox tag** auto-assigned to new documents and removed after processing; workflows can trigger on Document Added and filter by source (mail, API, consume folder); custom fields include Monetary and Document Link types; and the API accepts uploads at `POST /api/documents/post_document/` with tags and custom fields, returning a task id to poll ([paperless usage](https://raw.githubusercontent.com/paperless-ngx/paperless-ngx/dev/docs/usage.md); [paperless API](https://raw.githubusercontent.com/paperless-ngx/paperless-ngx/dev/docs/api.md)). These facts come from the dev-branch docs on GitHub, so check them against the installed release. An Android uploader that sits in the system share menu exists on F-Droid ([Paperless NGX Uploader](https://f-droid.org/de/packages/net.gmartin.paperlessngx_uploader/)).

Inference: the spec says "Documents: paperless is the document UI; the app only links", which is right, but it gives the tracker no view of invoices that arrived in paperless without an item — emailed invoices, a scanned handwritten bill. A small "Unlinked documents" attention entry, fed by a paperless inbox-tag query and offering ranked candidate items, closes the loop that Brex's unmatched tray closes. Inference: Ramp's Amazon caveat argues for the spec's existing choice to treat Amazon's *grand total* at order time as provisional and let the invoice amount, once attached, be shown beside it with a mismatch flag.

### Duplicates: soft flag, side-by-side, two choices

Expensify flags a potential duplicate on amount, currency and date, holds it, and resolves it on a side-by-side screen with **Keep all / Keep selected**; it also auto-dismisses clear non-duplicates with an "Explain" link ([Expensify duplicate detection](https://help.expensify.com/articles/new-expensify/reports-and-expenses/Duplicate-Detection)). Concur users report duplicates are warnings rather than hard stops (forum, secondary) ([Concur community](https://community.concur.com/t5/Concur-Expense-Forum/duplicate-expenses/m-p/10513)). The spec's hard/soft split, side-by-side panel and `Not a duplicate` / `Discard this item` buttons already follow this; nothing needs to change beyond showing *why* a pair matched ("same bill no + amount"), which is the Navan rationale column applied to duplicates.

## Reconciliation is a review queue that ends in zero and a lock

Personal-finance apps all separate "the bank says this happened" from "a human has confirmed what it is". Lunch Money imports rows as unreviewed and marks them with a grey check that turns green; bulk review asks for confirmation ([Lunch Money](https://support.lunchmoney.app/finances/transactions/transaction-status)). YNAB shows a banner counting transactions to approve, which filters the register when clicked ([YNAB approving](https://support.ynab.com/en_us/approving-and-matching-transactions-a-guide-ByYNZaQ1i.md)). Copilot caps its Mac "To Review" card at **25 items** specifically to stop users reviewing a hundred rows by accident ([Copilot](https://www.copilot.money/dispatch/to-review-card-for-mac)). The spec's Statement screen, where the Result cell is "the whole interaction" and progress reads `5 of 8 sorted`, is the same idea and is sound.

Three things the sources do that the spec does not. The first is **keyboard review**. Copilot on Mac uses arrows to move, `X` to select, `R` to mark reviewed and `C` to change category ([Copilot bulk editing](https://help.copilot.money/en/articles/7668990-bulk-editing-transactions)); Linear's triage uses `1` accept, `2` decline, `3` duplicate and `H` snooze, with `J`/`K` to move and `G` then a letter to navigate ([Linear Triage](https://linear.app/docs/triage); [Linear Inbox](https://linear.app/docs/inbox)). The spec's keyboard support stops at `n`, `/` and `Esc`. Inference: on the Mac, statement sorting is the one genuinely repetitive task, and `J`/`K` plus `1` Personal, `2` Lab — new item, `3` Match, `Enter` to confirm a suggestion would make a month's statement a keyboard-only pass. The same keys work for Amazon candidates.

The second is **a visible difference and a lock**. Actual shows cleared versus uncleared totals, a bar with the remaining difference against the statement balance, "All reconciled!" at zero and a "Lock transactions" button; editing a locked row warns ([Actual reconciliation](https://actualbudget.org/docs/accounts/reconciliation/)). YNAB locks reconciled rows and refuses imports dated more than three days before the last reconciled transaction as a duplicate guard ([YNAB reconciling](https://support.ynab.com/en_us/reconciling-accounts-a-guide-BJFE3fHys.md)). The spec deliberately has "no separate finish button". Inference: a count of rows sorted is weaker than a sum check, because a statement line missed by the parser is invisible to a row count; showing "Lab ₹15,030.00 · Personal ₹486.00 · Unsorted ₹740.00" against the statement's total debits, and locking the month at zero unsorted, gives the same reassurance Actual gives and matches the user's existing Working-to-Filed habit.

The third is **rules and dedupe**. Actual and Lunch Money both create rules from a corrected transaction, match on the raw bank text rather than the edited name, and preview affected rows before applying ([Actual rules](https://actualbudget.org/docs/budgeting/rules/); [Lunch Money rules](https://support.lunchmoney.app/setup/rules)); Copilot warns that its rules cannot be undone and tells users to review the list first ([Copilot](https://www.copilot.money/dispatch/transaction-category-rules)). For re-imports, Actual checks a transaction id and falls back to fuzzy date, amount and payee, while Firefly III offers a content hash computed after column mapping — so changing the mapping changes the hash (search-snippet evidence only) ([Actual importing](https://actualbudget.org/docs/transactions/importing/); [Firefly III](https://docs.firefly-iii.org/references/data-importer/duplicate-detection/)). Inference: a one-click "Always personal: SWIGGY" on a sorted line, stored as a narration-substring rule and shown as a *Suggested* result on later imports rather than applied silently, would shrink each month's pass; because the same merchant can be both lab and personal for this user, suggestion-with-confirm is safer than auto-apply. Inference: the UPI narration in the sample data carries a 12-digit reference, which one vendor source calls the reconciliation key for UPI ([imagetotable.ai](https://imagetotable.ai/extract/phonepe-screenshot)); storing it per line gives a stable dedupe id for savings-account rows, with a hash of date, amount and narration as the fallback for credit-card statements.

On match windows the sources disagree in a useful way. Ramp uses one calendar day for receipts ([Ramp matching](https://support.ramp.com/troubleshooting-transaction-receipt-matching)); YNAB matches a manual entry to an imported one on identical amount and dates **within 10 days**, keeping the bank's amount and the user's date, payee and memo, with unmatch always available ([YNAB approving](https://support.ynab.com/en_us/approving-and-matching-transactions-a-guide-ByYNZaQ1i.md)). The spec uses exact paise and ±2 days. Inference: keep ±2 days for auto-match, since a wrong silent match in a reimbursement record is costly, but widen the *Suggested* tier to roughly ±10 days so a mistyped date surfaces as a one-click confirm instead of an unsorted line plus an orphan item.

Row anatomy is the one area where sources give concrete glyphs. YNAB uses a green or grey "c" for cleared, a lock for reconciled and a circled "i" for unapproved; Actual uses a grey-to-green circle and a lock; Lunch Money puts a check at the far right and selection boxes at the left ([YNAB reconciling](https://support.ynab.com/en_us/reconciling-accounts-a-guide-BJFE3fHys.md); [Actual reconciliation](https://actualbudget.org/docs/accounts/reconciliation/); [Lunch Money](https://support.lunchmoney.app/finances/transactions/transaction-status)). Actual also keeps the original bank text as a separate "imported payee" field next to the cleaned one ([Actual rules](https://actualbudget.org/docs/budgeting/rules/)). Inference: statement rows should show a cleaned payee ("New Era Ply") as primary text and the raw monospace narration as a muted second line or hover, rather than the truncated raw narration the spec puts first.

## The payment form: a full page, a native keypad and one hard rule

This is the screen used most often and under the worst conditions — standing at a counter, one hand, straight after a UPI payment — so it gets the most detail. The research supports most of the spec's field choices and overturns three implementation decisions: the container, the validation gate and the placeholder-as-label.

### Use a full-screen page, not a bottom sheet

NN/g's guidance on bottom sheets is that they suit quick contextual tasks, should not hold lengthy or complex content, **do not improve reachability** (the middle of the screen is usually easiest to tap), must support Back and need a visible Close button rather than swipe-only dismissal ([NN/g bottom sheets](https://www.nngroup.com/articles/bottom-sheet/)). The spec's Add is a bottom sheet on phone containing amount, description, a three-way kind selector with conditional reveals, account chips, attachments and a More section. Inference: with the keyboard open, a sheet holding that much is mostly obscured, and the form is the whole task rather than a side-task of the Open list; a full-screen route also gives the Android share target somewhere to land and makes the system Back gesture behave predictably. Keep the 420px modal on the laptop.

Android's guidance adds that touch targets should not sit under gesture-navigation insets and that content must respect window insets with the keyboard ([Android system bars](https://developer.android.com/design/ui/mobile/guides/foundations/system-bars)). Inference: pin a full-width Save button above the keyboard with safe-area padding. The specific web mechanisms (`env(safe-area-inset-bottom)`, `visualViewport`) were not verified in the research and need testing on the actual phone.

### Amount: text input, decimal keypad, live Indian grouping

GOV.UK's instruction is blunt: do not use `<input type="number">` unless research shows a need, because scrolling can change the value and non-numeric input gets no clear feedback; use a text input with `inputmode="decimal"` ([GOV.UK text input](https://design-system.service.gov.uk/components/text-input/)). MDN confirms `inputmode="decimal"` produces a numeric keypad with the locale's decimal separator, and stresses that it **enforces nothing** — validation is separate ([MDN inputmode](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_Attributes/inputmode)). The prototype already does this (`inputmode=decimal` on `#f_amount`); the spec text just says "numeric keypad" and should be made explicit so a rebuild does not regress to `type="number"`.

GOV.UK also says to place the currency symbol as a prefix outside the input **and** name the unit in the label, because screen readers may skip prefixes, and to accept a pasted or typed symbol without raising an error ([GOV.UK text input](https://design-system.service.gov.uk/components/text-input/)). NN/g's mobile checklist says the same thing from the other side: accept any format and autoformat it, support paste ([NN/g mobile input checklist](https://www.nngroup.com/articles/mobile-input-checklist/)). For display, `Intl.NumberFormat("en-IN")` produces lakh grouping natively ([MDN Intl.NumberFormat](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/NumberFormat)).

Inference: the parser should strip `₹`, commas and spaces, so that an amount copied from a payment app ("₹1,23,456.00") pastes cleanly; store the raw number and group it live as the user types. Inference: nothing found supports building a custom on-screen keypad — no study comparing speed was located, and it would forfeit paste and system accessibility. No source gives an evidence-based size for the amount; the spec's 32px/600 is a reasonable aesthetic choice, not a researched one. Whether Gboard shows "." on the decimal keypad for an en-IN device was not verified and must be tested.

### Labels above, no placeholders standing in, defaults from history

GOV.UK and NN/g agree that labels go above fields, are short and sentence-case, and that **placeholder text must not replace a label or hint** ([GOV.UK text input](https://design-system.service.gov.uk/components/text-input/); [NN/g mobile input checklist](https://www.nngroup.com/articles/mobile-input-checklist/)); WCAG adds that placeholder text is not exempt from the 4.5:1 contrast requirement ([WCAG 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)). The spec describes the What field only by its placeholder, "Plywood, cab to market…", and the prototype's amount field uses a `0` placeholder inside a ₹ label. Each field needs a visible label ("Amount in rupees", "What was it for"), with the examples moved to hint text.

On defaults, NN/g recommends setting them from input history and frequently used values, computing values from other input, and autocompleting from the first letters typed; for mutually exclusive choices it recommends pre-selecting the most common option, and warns that horizontal radio layouts can be hard to scan and that labels must be tappable because the controls themselves are small ([NN/g mobile input checklist](https://www.nngroup.com/articles/mobile-input-checklist/); [NN/g radio defaults](https://www.nngroup.com/articles/radio-buttons-default-selection/)). WCAG 3.3.7 requires that information already entered in a process be auto-populated or selectable rather than re-typed ([WCAG 3.3.7](https://www.w3.org/WAI/WCAG22/Understanding/redundant-entry.html)). Cashew, an open-source budget app, auto-assigns categories to repeated titles and duplicates frequent transactions from a long-press on the add button, though this comes from a search summary, not a fetched page ([Cashew FAQ](https://cashewapp.web.app/faq.html)).

The spec's last-used Paid from, default Kind of Shop, and Paid on defaulting to today all follow this. Inference: go one step further with **vendor memory** — choosing or typing a known vendor sets Kind and the usual account (Robu.in implies Online order; City Cabs implies Service), removing a tap on repeat purchases. Inference: because a wrong account on a reimbursement record matters more than a wrong category in a budget app, the pre-selected account must stay visible on the main form, not folded into More. Inference: Kind (three options) and Paid from (two) are small, required, mutually exclusive sets, so visible segmented chips with one pre-selected beat a dropdown; no retrieved source tests chips against dropdowns directly, and the two secondary sources on mobile dropdowns disagree ([DOL](https://dol.gov/agencies/eta/ui-modernization/mobile-usability/mobile-form-design); [Smashing](https://www.smashingmagazine.com/2018/08/best-practices-for-mobile-form-design)). The three Kind labels — "Online order", "Shop", "Service / no delivery" — are long for one row on a narrow phone; given NN/g's caution on horizontal layouts, shorten them or stack them, and make the whole chip the target.

### Only amount blocks saving; everything else becomes "incomplete"

NN/g's first question for any field is whether it is needed at all ([NN/g mobile input checklist](https://www.nngroup.com/articles/mobile-input-checklist/)). Splitwise's add screen, per a third-party critique, requires just description and amount ([Pratt IxD](https://ixd.prattsi.org/?p=3982)). The spec requires Amount and What and keeps **Save disabled** until both are filled.

Two cited rules bear on that. Baymard found testers frustrated by errors shown before they had a chance to type, recommends validating on blur and clearing the error on the keystroke that fixes it, and notes inline validation does not replace submit-time handling ([Baymard](https://baymard.com/blog/inline-form-validation)); NN/g says to keep messages next to the field and never rely on a summary alone ([NN/g form errors](https://www.nngroup.com/articles/errors-forms-design-guidelines/)). WCAG 3.3.1 requires an error to be identified and described **in text**, and notes that native browser validation bubbles disappear, may not scale with zoom and expose only the first error ([WCAG 3.3.1](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html)). A silently disabled button describes nothing.

Inference: keep Save always enabled; on tap with no amount, show "Enter an amount, like 450" beside the field (GOV.UK's "Enter [x]" pattern ([GOV.UK text input](https://design-system.service.gov.uk/components/text-input/))) and focus it. Inference: drop What as a hard requirement on the phone. The user can attach the payment screenshot, type the amount and leave; the item is saved with an "Incomplete" reason and surfaces in Needs attention on the laptop. This is what makes the 15-second target robust, and it mirrors Lunch Money's model where editing a row implicitly clears its review state ([Lunch Money](https://support.lunchmoney.app/finances/transactions/transaction-status)). The counter-argument is that a bare amount is hard to recognise three days later; the screenshot and the timestamp are the mitigation, and the statement narration will supply the payee at reconciliation.

Other field hygiene from GOV.UK: avoid `maxlength` because it silently truncates pasted text, and set `spellcheck="false"` on reference numbers and names ([GOV.UK text input](https://design-system.service.gov.uk/components/text-input/)) — relevant to Order no. and Bill no.

### Progressive disclosure is right, with a caveat about hidden length

The spec's collapsed More (Paid on, Bill no, Purpose, Remarks) matches the principle of showing only what the step needs. One secondary source cautions that heavy progressive disclosure distorts expectations of a form's size ([Queensland Government](https://www.qld.gov.au/web/cue/module4/checkpoints/checkpoint21/)). Inference: the conditional reveals under Kind are the bigger risk than More — choosing "Online order" grows the form by two controls under the user's thumb. Reserve the space or animate the reveal, and keep Save pinned so it does not jump.

### Screenshot-first capture via the Android share target is feasible, with conditions

A PWA can appear in Android's share sheet and receive images and PDFs by declaring `share_target` in its manifest with `method: "POST"`, `enctype: "multipart/form-data"` and `params.files`; the docs advise listing both MIME types and extensions ([MDN share_target](https://developer.mozilla.org/en-US/docs/Web/Manifest/share_target); [Chrome for Developers](https://developer.chrome.com/docs/capabilities/web-apis/web-share-target)). The constraints are firm: the PWA **must be installed**, the foreground page cannot read the POST body so a service worker must intercept it, stash the file (Cache or IndexedDB) and answer with a 303 redirect, and there is one share target per manifest ([MDN share_target](https://developer.mozilla.org/en-US/docs/Web/Manifest/share_target); [Chrome for Developers](https://developer.chrome.com/docs/capabilities/web-apis/web-share-target)). MDN marks the feature experimental with limited availability; Chrome documents it from Chrome 76 on Android. Installability requires HTTPS, a manifest with name, 192px and 512px icons, `start_url` and a standalone-type display mode ([web.dev](https://web.dev/articles/install-criteria)).

The spec lists "Offline mode / sync" as out of scope and mentions the share target only as a tip line. Inference: those two decisions collide. A share target needs a service worker anyway, and a self-hosted instance on a private network needs a real HTTPS certificate for installability; these are architecture requirements that should be in the spec now, even if offline queuing is deferred. Inference: when the app is opened by a share, the form should open with the image attached, typed as Payment proof, amount focused — the spec's intent, now with a known mechanism.

OCR stays out of the save path. UPI screenshots typically contain amount, payee, date/time and a 12-digit reference, but labels differ by app (PhonePe "UPI Ref No", GPay "Transaction ID", Paytm "UTR Number") and Indian grouping is commonly misparsed; all of this is vendor or forum evidence, and nothing was found on CRED's own receipt layout ([imagetotable.ai](https://imagetotable.ai/extract/upi-screenshot); [UiPath forum](https://forum.uipath.com/t/extracting-data-from-payment-screenshot-like-gpay-phone-pay-yono-paytm-etc/5723617)). Ramp's stance on its camera-roll matching is that nothing is used until the user reviews and confirms ([Ramp](https://support.ramp.com/auto-match-receipts-from-your-camera-roll)). The spec's decision to exclude OCR from v1 is supported; if it is added later, extracted values belong in editable fields as suggestions, marked as such.

### After save: undo, not confirm

Material's guidance (via search summary) favours an Undo action on a snackbar; platform implementations treat a snackbar *with* an action as persisting until dismissed, and Flutter changed its default to match the Material 3 spec ([Material snackbars](https://material.io/components/snackbars); [Flutter](https://docs.flutter.dev/release/breaking-changes/snackbar-with-action-behavior-update)). The spec's "5-second Undo toast" has no official source behind the number — the commonly quoted four seconds appears only in third-party libraries. Inference: on a phone at a shop counter the user has usually pocketed the device within five seconds, so the toast should persist until the next interaction, and the just-saved row should keep an Undo affordance in the list. The spec's duplicate warning on save ("Looks like *Spray Paint ₹250.00, filed in January1*" with Save anyway / Discard) is consistent with the soft-warning pattern above and should stay.

## Colour whispers status; shape, words and tabular rupees carry it

### About five hues for seven stages, never colour alone

Carbon states that relying solely on colour for status is insufficient and that indicators should pair colour with a shape, symbol or text label; it recommends **about five or six indicators at most**, placing the indicator before its label, and never reusing one shape in different colours ([Carbon](https://carbondesignsystem.com/patterns/status-indicator-pattern/)). Its colour semantics are: red for error, orange and yellow for warnings, green for success, blue for passive or workflow progress, grey for draft or unstarted ([Carbon](https://carbondesignsystem.com/patterns/status-indicator-pattern/)). Atlassian's lozenge guidance adds sentence case rather than capitals, short labels, and again a text label plus an icon where helpful ([Atlassian](https://atlassian.design/components/lozenge/usage)). WCAG 1.4.1 makes the non-colour cue a Level A requirement, and 1.4.11 asks for 3:1 on graphics needed to understand content unless the same information is in visible text ([WCAG 1.4.1](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html); [WCAG 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)).

The spec's five-hue budget (grey, amber, red, green, blue) already sits inside Carbon's cap, and "every badge has words" satisfies 1.4.1. Three refinements follow. First, the spec uses the same pill form for stage and for attention reasons, and gives amber to two stages (Refund pending, Needs invoice) and green to two (Ready, Reimbursed). My own calculation shows why words are doing all the work: the light-theme amber tint against the green tint is **1.04:1**, and the amber tint against the white surface is 1.12:1, so the pill backgrounds are effectively invisible as differentiators.

Inference: add a small leading glyph that encodes *progress* by shape — an empty, partly filled and filled circle across the waiting stages, a check for Reimbursed, a struck circle for Closed — so order reads without colour, and reserve a visibly different form (outlined, with a warning icon) for attention badges so "stage" and "problem" differ by shape. Second, the section headers are specified as uppercase and letter-spaced; Atlassian's rule is about lozenge labels specifically, so extending sentence case to headers is my inference, but the reasoning (shape recognition, calm) carries. Third, reason badges such as "Not delivered · 11 d" already contain the stage, so a flagged row should show the reason badge alone rather than stage plus reason.

By my own calculation, every text-on-surface and badge pair in the spec's palette meets 4.5:1: light theme ranges from **4.59:1** (status grey `#6B6B6B` on `#EEEEEC`, the only marginal pair) to 16.65:1 for body text, and dark theme from 5.92:1 to 15.74:1. Borders are 1.27:1 (light) and 1.23:1 (dark). That is acceptable for row dividers, but WCAG 1.4.11 requires 3:1 for the boundary of a control when nothing else identifies it ([WCAG 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)), so text inputs and unselected chips drawn only with that hairline fail; they need a stronger input-border token.

### Tables on the Mac, two-line rows on the phone, user-chosen density

Carbon defines row heights of 24, 32, 40, 48 and 64px ([Carbon data table](https://carbondesignsystem.com/components/data-table/style/)). NN/g recommends frozen headers on long tables, light borders or zebra striping and hover highlight to keep one's place, and — for mobile — keeping a real table with a locked first column and visible scroll cues rather than assuming a card transform, designing the large-screen table first and then deciding which attributes matter ([NN/g data tables](https://www.nngroup.com/articles/data-tables/); [NN/g mobile tables](https://www.nngroup.com/articles/mobile-tables/)). Linear lets users pick which properties appear on a row, toggles list and board with one key, and separates grouping, ordering and filtering; its redesign aimed to cut visual noise while keeping density, with muted inactive text ([Linear display options](https://linear.app/docs/display-options); [Linear redesign](https://linear.app/now/how-we-redesigned-the-linear-ui)).

The spec's 40px laptop rows and 64px two-line phone rows land exactly on Carbon's md and xl sizes. No source compares table, board and inbox layouts for expense lists — help centres are silent on row layout — so the choice among the prototype's three variants rests on inference. Inference: treat them as Linear treats list and board, as **views of the same grouped data, not competing products**. The Inbox variant is the default on both devices because it is the only one built around the attention queue that every vendor leads with. The Ledger table is the Mac view for batch selection, statement work and search, where right-aligned amount columns and multi-select pay off. The Board is the weakest fit as a primary view: stage columns suit items a user drags between states, but here most transitions are single-tap or automatic, the terminal columns grow without bound, and on a phone the prototype already collapses it to one column at a time. Keeping it as an optional toggle costs little; making it the home screen would bury the overdue queue. The Mac table has ten columns; a display-properties control (or simply hiding Order/Bill no. and Docs below a width) follows Linear's model and NN/g's "let users pick attributes".

### Money: tabular figures, fixed paise in rows, en-IN everywhere

`font-variant-numeric: tabular-nums` gives digits equal width so columns align, but only when the font carries the feature ([MDN font-variant-numeric](https://developer.mozilla.org/en-US/docs/Web/CSS/font-variant-numeric)). Shopify's Number component applies tabular numerals automatically and notes that currency symbols keep their normal width ([Shopify](https://shopify.dev/docs/api/app-home/latest/web-components/typography-and-content/number)). Linear uses Inter with Inter Display for headings ([Linear redesign](https://linear.app/now/how-we-redesigned-the-linear-ui)). No official typography source was found for Stripe, Mercury, Ramp or Copilot; claims about them circulate only in third-party breakdowns and are left out.

The spec specifies a system UI stack with tabular figures. Inference: the system stack resolves to different fonts on the Mac and the Android phone, so tabular support and the ₹ glyph's width and weight will differ between the two devices; either verify both or ship one font known to have `tnum` (Inter is the obvious candidate, though its feature support was not confirmed from a primary source in this research). Inference: keep two fixed decimals in every list row — receipts are exact, and with tabular figures and right alignment the decimal points then align for free — and de-emphasise paise in a smaller, muted span only in the large summary figure, using `formatToParts()`.

For formatting, MDN confirms `en-IN` yields lakh grouping (`1,23,456.789`) ([MDN Intl.NumberFormat](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/NumberFormat)). Own run in Node v26.13.0: `style:'currency', currency:'INR'` under `en-IN` gives `₹1,23,456.00`; negatives render as `-₹1,234.50`; `signDisplay:'always'` gives `+₹1,234.00`; compact notation gives `₹1.2L` and `₹1.2Cr` but `₹45K` for 45,419.87; and the locale matters — `en-US` with INR produces Western grouping. Output is engine-dependent and should be rechecked on Android Chrome and Safari. Inference: avoid compact notation altogether. The summary line is the only candidate, and at this user's scale (tens of thousands of rupees) compact mode yields "K", which mixes Western and Indian systems; the full `₹45,419.87` fits on one line. The prototype formats with `toLocaleString('en-IN')` plus a hand-prepended `₹`; switching to the currency style handles negative placement (`-₹` rather than `₹-`) for refunds without extra code.

Refund credits deserve a rule of their own. Carbon's differential indicators pair a sign or arrow with the value and treat colour as optional ([Carbon](https://carbondesignsystem.com/patterns/status-indicator-pattern/)). Inference: show refunds and reimbursement credits with an explicit `+` and the word "Refund" or "Reimbursed", never green alone.

### Dark mode and accessibility floors

Material's dark-theme guidance, seen only through search summaries because the pages did not load, recommends dark grey rather than black for the base surface and lighter surfaces at higher elevation, with Material 3 expressing elevation as tonal surface-container roles ([Material 2 dark theme](https://m2.material.io/design/color/dark-theme); [M3 tone-based surfaces](https://material.io/blog/tone-based-surface-color-m3)). Linear generates its themes in LCH from three inputs — base, accent, contrast — and Stripe built its palette in a perceptually uniform space so contrast is consistent across hues ([Linear redesign](https://linear.app/now/how-we-redesigned-the-linear-ui); [Stripe](https://stripe.com/blog/accessible-color-systems)). The spec's dark tokens (`#141414` background, `#1E1E1E` surface) follow the grey-not-black rule. It defines two surface levels; the side panel, sheet and popovers sit above rows and, with no shadows in the visual direction, need a third, lighter step to read as raised in dark mode.

The accessibility floors are few and concrete. Text contrast 4.5:1, large text 3:1 ([WCAG 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)). Targets at least 24×24 CSS px at AA, 44×44 at AAA ([WCAG 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)); NN/g's physical recommendation is 1 cm × 1 cm with primary actions larger, and it notes spacing cannot rescue a too-small target ([NN/g touch targets](https://www.nngroup.com/articles/touch-target-size/)). A visible focus indicator is required, and the AAA criterion describes a 2px perimeter with a 3:1 change ([WCAG 2.4.13](https://www.w3.org/WAI/WCAG22/Understanding/focus-appearance.html)). The spec says "touch targets ≥ 44px" but also specifies 12px badges, a `⋯` overflow and an `×` to unmatch; those small controls are where the 44px promise usually breaks, and on a laptop the 40px rows' inline buttons still need 24px. The spec says nothing about focus styling, which a keyboard-first Mac review depends on. The Atlassian note that truncated lozenge text is unrecoverable because lozenges cannot take focus ([Atlassian](https://atlassian.design/components/lozenge/usage)) applies to `Already filed in <batch>` with long batch names such as "Mysore–BLR Trip": truncate the row text, not the badge.

## Conclusion

The research did not find a better concept than the one in `DESIGN.md`; it found that the concept is the industry's consensus, arrived at independently, and that the remaining risk lies in three seams the spec treats as simple. The first is the edge of the queue: without snooze and "can't provide", a list of things-to-do becomes a list of things-that-are-red, and the Navan and Spendesk designs exist precisely because of that decay. The second is the end of each loop — a reconciled month and a reimbursed batch are currently states the user asserts, where the mature tools make them states the data proves (difference at zero, credit seen) and then lock. The third is the phone form's contract: once only the amount is mandatory and everything else becomes a laptop-side "incomplete" reason, the phone and the Mac stop being two layouts of one app and become two halves of one workflow, capture and judgment, which is what the user's "quick-entry + review" framing asked for.

What remains unknown is mostly visual and empirical: no primary source documents badge colours, row layouts or amount-field sizes for any expense product; Material 3 and Apple HIG component guidance could not be retrieved; and the Gboard decimal key, ₹ glyph metrics across system fonts, share-target behaviour on the user's actual phone and the payment app's share affordance all need a ten-minute device test rather than more reading. Those tests should precede any polish, because each can invalidate a design choice that looks settled on a laptop.

## Prioritised changes to `mockup/DESIGN.md`

Section references are to the current spec. Priority reflects impact on daily use divided by effort in the prototype.

### Supported by sources

1. **§3.2 Add — make it a full-screen page on phone, not a bottom sheet; keep a visible Close and Back support.** Sheets suit short contextual tasks, do not aid reachability and need explicit close ([NN/g](https://www.nngroup.com/articles/bottom-sheet/)).
2. **§3.2 Add — replace "Save disabled until Amount > 0 and What non-empty" with an always-enabled Save and an inline text error on the amount field, validated on blur and cleared on fix.** Errors must be described in text next to the field; premature and invisible validation frustrates users ([WCAG 3.3.1](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html); [Baymard](https://baymard.com/blog/inline-form-validation); [NN/g](https://www.nngroup.com/articles/errors-forms-design-guidelines/)).
3. **§3.2 Add — give every field a visible label above it; move "Plywood, cab to market…" to hint text; label the amount "Amount in rupees" alongside the ₹ prefix.** Placeholders must not replace labels; prefixes may be skipped by screen readers ([GOV.UK](https://design-system.service.gov.uk/components/text-input/); [NN/g](https://www.nngroup.com/articles/mobile-input-checklist/)).
4. **§3.2 Add — specify the amount as a text input with `inputmode="decimal"` (never `type="number"`), tolerant of pasted `₹` and commas, no `maxlength`; `spellcheck="false"` on Order no. and Bill no.** ([GOV.UK](https://design-system.service.gov.uk/components/text-input/); [MDN](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_Attributes/inputmode)). 5. **§5 Needs attention — add a "No bill exists / can't provide" resolution that stops the nudge, and record it as a remark.** ([Spendesk](https://helpcenter.spendesk.com/en/articles/4153508-missing-receipts-send-reminders); [Ramp](https://support.ramp.com/hc/en-us/articles/360042588454-Submitting-receipts-memos-and-accounting-for-your-Ramp-transactions)).

13. **§3.5 Statement — offer "Always treat this payee as personal/lab" from a sorted row, matching on raw narration, with a preview of affected lines.** ([Actual](https://actualbudget.org/docs/budgeting/rules/); [Lunch Money](https://support.lunchmoney.app/setup/rules)).
