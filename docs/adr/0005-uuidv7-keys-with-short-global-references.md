# UUIDv7 keys inside, short global references outside

Every record has two identifiers. The database key is a **UUIDv7** (RFC 9562, generated by Postgres 18's `uuidv7()`): time-ordered, so index inserts stay cheap; unguessable, so URLs and API paths leak nothing about volume or other Claimants; never shown to people. The **Reference** people see is a type letter plus one global, gap-tolerant sequence per type, with no zero padding: `E-213` (Expense), `B-431` (Bill), `R-12` (Refund), `O-1` (Owed to university), in the style of issue keys (`PROJ-123`). A Reference never changes once issued, is unique across all Claimants, and is what paperless custom fields, attention items and conversations use. Claims keep their own name (`2026/November1`). The vendor's Bill number is a separate field and is never replaced by either.

## Considered Options

- **Per-Claimant sequences** (`E-12` for each person): rejected; the same label would mean different records, and paperless fields are shared across owners.
- **Bigint identity as the only key, shown directly**: simplest, but exposes record counts in URLs and invites guessing other Claimants' records.
- **Prefixed opaque IDs only** (`exp_01JD9…`, TypeID/Stripe style): good for APIs, too long to say aloud or type into paperless.
- **Zero-padded references** (`E-0213`): breaks its own format at 10,000 and adds nothing.

## Consequences

- References come from Postgres sequences; a rolled-back transaction can skip a number, which is acceptable.
- APIs accept either form; responses carry both.
